# Pragma Space and Candidate Generation Policy

## Purpose

The HLS-DSE framework explicitly separates three decisions:

1. **Pragma-space definition** — which directive families, locations, parameters, and legal values are allowed.
2. **Candidate generation/selection** — which concrete pragma configurations are constructed and evaluated.
3. **Evidence selection** — whether a candidate is evaluated locally or jointly, and at which fidelity.

These are distinct layers and must not be conflated.

## User control

The benchmark owner/user may define the allowed pragma space and hard constraints. The framework may then automatically generate concrete candidate configurations inside that declared space.

The framework MUST NOT silently introduce a new pragma family, source-code transformation, parameter range, or legality assumption that is absent from the declared space. Any framework-generated extension requires an explicit recorded policy/configuration change and a new experiment version.

## Candidate generation

Candidate configurations may be generated by exhaustive enumeration, random sampling, Bayesian optimization, evolutionary search, rule-based generation, or another declared method. The generation method is part of the experiment provenance.

A candidate is a concrete assignment such as:

```yaml
pipeline: true
unroll:
  loop: loop_17
  factor: 4
array_partition:
  variable: A
  type: cyclic
  factor: 2
```

## Legality

Every candidate receives an explicit status:

- `LEGAL`
- `ILLEGAL_DECLARED_CONSTRAINT`
- `ILLEGAL_TOOL_REJECTED`
- `INVALID_GENERATOR_OUTPUT`
- `UNKNOWN`

Illegal candidates must remain traceable but must not be presented as successful HLS measurements.

## No silent expansion

If the system discovers that a useful configuration is outside the current space, it records the candidate with `legality_status: OUT_OF_SPACE_CANDIDATE` (`schemas/PRAGMA_CANDIDATE_SCHEMA.json`). It does not silently expand the search space.

## Relationship to the research contribution

Automatic pragma generation/selection is an enabling capability and is not, by itself, claimed as the novelty of this project. The central research question remains the value of selecting local versus joint/expensive evidence under a fixed evaluation budget.

## Required provenance

Every candidate must record:

- benchmark/workload ID
- source version
- pragma-space version
- generator ID/version
- generator seed, when applicable
- concrete pragma configuration
- legality status
- generation timestamp
- parent candidate/configuration, when applicable
- evaluation status

## Reproducibility

Given the same source snapshot, pragma-space specification, generator version, seed, and tool environment, candidate generation must be reproducible whenever the generator claims deterministic behavior.
